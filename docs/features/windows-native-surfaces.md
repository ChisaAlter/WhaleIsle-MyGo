# Windows native notifications and desktop glass

Windows notifications use WinRT `ToastNotificationManager` and `ToastNotification`, through syscall with `CGO_ENABLED=0`. The tray remains an icon/menu and never presents a notification-area balloon as a toast.

`NotificationOptions.Toast` accepts a full Windows toast XML document or builds `ToastGeneric` from title/subtitle/body, icon, hero, foreground actions, duration, scenario and silent options. Custom XML preserves adaptive groups, progress, attribution, inputs and Windows schema attributes; foreground launch/action arguments receive an ID envelope so live and cold activations preserve notification identity and action values. Native XML parsing and delivery HRESULTs are returned. A new unpackaged AUMID can have no notification setting until its first Show; only that `ERROR_NOT_FOUND` state defers to the one actual Show result.

Tag/group keys are stable 16-character hashes and the full original ID is carried in XML. `NotificationHistory` reads delivered records without changing them. `Close` removes only the corresponding active notification; startup and shutdown never clear notification-center history. `ClearNotifications` is explicit and clears only the app identities this process owns. Timeout hides the banner while retaining history-click callbacks. User dismissal releases listeners. `OnAction`, `OnClose` and `OnFailed` run on the UI thread; native callbacks copy their data and post to the app message window. Reference-counted COM delegates and the class factory use fixed startup callback tables.

The Go shell has a separate toast activator CLSID, `{9CC711B1-3FB8-4C05-AB6C-CF32C5077B0F}`. Setup writes the shortcut AppID/activator property and exact current executable's `LocalServer32` command only behind the desktop-system-integration gate. Existing foreign or customized links and another install's command are preserved. Isolated/portable desktops do not register the product identity or issue system notifications. Regular local builds may use their registered identity, since the Go presenter never creates `Electron.lnk`.

A COM-launched invocation handles only its explicit server flag before taking the single-instance lock. Its STA receiver has a ten-second deadline, accepts one activation and asks later concurrent calls to retry. The base64 JSON handoff has bounded size, strict schema and app identity, and is consumed once. It dispatches inert notification data and never executes an argument or URI. Current per-notification listeners own their routes; an older run's otherwise unknown ID safely reveals the desktop. Retained factory/callback references fail with `CO_E_OBJNOTCONNECTED` after revoke rather than touching released objects.

Legacy migration examines only `Electron.lnk` in Programs and requires the exact same executable, AppID, empty arguments and uncustomized icon. It backs up original bytes to an app-owned unique directory; a different Electron installation, pins and other user links are preserved. Uninstall uses a standalone windowsgui helper embedded in the uninstaller. It preflights the exact COM command and flat Go link's target, AppID, activator CLSID, arguments and icon before deletion; unknown registry values/subkeys are preserved. It does not remove shared Programs directories or notification history. The installer stores `NativeNotificationTarget` beside `NativeInstallID`, remembers/restores it during rollback, and leaves it unchanged when a failed uninstall retargets the current payload location. After the manifest ID, runtime and current install location prove the uninstall record belongs to this installation, cleanup uses that original target and still verifies the actual command/link. Old records missing the field fall back only to the explicit uninstall source; an old retired retry preserves unmatched original-path registrations. An empty or invalid existing field is rejected by the helper instead of inferring a target from COM.

Deep-color, image-less native desktops select `VibrancyAcrylic` on their existing DirectComposition window. DWM performs live desktop blur; an inexpensive cached elliptical vignette and dim veil preserve contrast. Wallpapers/gradients continue through the existing image sampler and disable the system material. Light appearance and hidden wallpaper stages disable it. The Windows backend checks composition, high-contrast settings, API HRESULTs and the actual `DWMWA_SYSTEMBACKDROP_TYPE` value before reporting material availability, and restores the disabled state in place. Windows before 11 22H2 cannot provide this documented system backdrop; the API reports no material there.

Verification uses the hidden-console runner with no installed desktop process or real product profile. Native opt-in fixtures cover real WinRT XML/history/tagged replacement/targeted removal, DWM Acrylic/Mica enable/read-back/disable on a composed native window, COM activation with user input, retained interfaces after revoke, burst rejection, and a separate windowsgui COM-server cold launch with a unique temporary CLSID. Core/fake tests cover options, main-thread event order, timeout history, dismissal release, replacement during activation and delivery errors. Shortcut and owned-unregister tests use temporary files and unique test registry paths. The notification NSIS include was compiled with the actual NSIS compiler and run with an argv-recording windowsgui fixture helper in a unique test registry namespace: a changed retired location retains the original notification target, a missing field uses only the explicit legacy uninstall source, and an unowned invocation does not run the helper. Source contracts additionally check the installer write, rollback and retry invariants. This fixture covers notification target handoff; it does not claim a full production payload uninstall. Cross-platform builds retain the ordinary notification implementations; Windows-specific template/activator requests return unsupported on other backends.

The native tests exercise the actual WinRT/DWM/COM APIs and a separate server process. They do not drive the real Windows Notification Center UI or physically click a toast/action; final delivery appearance and end-to-end notification-center activation still need that interactive desktop check. The DWM fixture reads the actual material state but does not claim a captured visual comparison of desktop blur or vignette. macOS/Linux behavior is compile-checked here; those desktops are not available for native runtime verification in this Windows session.
