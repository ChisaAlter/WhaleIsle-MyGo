# Desktop pet renderer and overlay parity

The rendering chain remains THA4 (when enabled and its fixed-manifest resources verify), the bundled original layered rig, a selected sprite sheet, then the basic animated head. A fresh profile prefers THA4 while the pet itself remains disabled; an existing namespace with an omitted neural field retains the prior false interpretation. Explicit true and false now persist without omission. Because earlier false values were omitted, their intent cannot be recovered independently. Explicit skin selection skips the default rig. Closing, late resource completion, provider failures, per-frame failures, sleep and output disposal retain their lifecycle checks. Nothing downloads a model or runtime at startup.

Released builds use the executable-adjacent `pet-render-assets` directory. An unstamped/development build can instead explicitly set `WHALEISLE_PET_RENDER_ASSETS` to an absolute directory; a relative or invalid override does not fall through to another directory. The resource loader applies the compiled path, size and SHA-256 allowlist to either source. This is content verification, not a digital signature.

## Character and overlay geometry

The character has a 240×260 CSS stage at scale 1. It no longer receives a second 88×110 CSS reduction or a permanently reserved 178px status panel. Status and dialogue float near the character and clamp to its active display work area.

The current reference function is `reference/electron/src/main/desktop-live2d.js:663–676`: it covers **one active display**, hopping with the character. Its old file-header statement about a union of all monitors is stale. Selection now follows its fixed nominal centre first, then the anchor, then the primary display. Reference uses a constant offset of 120×130 DIPs even when growth changes the drawn size. On Windows that offset is converted into physical pixels using the monitor containing the anchor. It never depends on the mutable drawn width, target HWND DPI or growth preference, so resizing on the newly selected display cannot feed back into a different choice. Other platforms use the same constant offset directly in DIPs.

This restores centre-first selection in place of the temporary anchor-first workaround. For unequal-DPI screens the explicit anchor-monitor conversion is this port's mapping between physical desktop space and nominal DIPs; it does not claim Electron's global DIP monitor layout is numerically identical. A character straddling the boundary can be clipped by the selected display's single overlay, as in the reference one-display design.

Windows pet placement, cursor samples, physics bounds and hit tests share physical desktop pixels. The pet-specific helpers use native monitor bounds, GetCursorPos, actual HWND content origin and SetWindowPos. The page receives `(physical − actual HWND origin) / HWND scale` exactly once. The global MyGo Screen/Window APIs are unchanged. Other platforms retain their DIP coordinate contract. The Windows helper temporarily permits synchronous programmatic movement and immediately restores the move restriction: MyGo's `WM_WINDOWPOSCHANGING` otherwise applies `SWP_NOMOVE` even to application `SetWindowPos`, leaving the overlay on its old display while changing only its size. Browser DPR and viewport updates after a DPI hop are asynchronous; measurements wait for both to match the actual HWND rather than treating a matching character rectangle alone as completion.

Saved Windows positions use `space: "windows-physical"`; old empty-space MyGo DIP anchors are converted using the matching historical monitor scale. Unmatched old positions use the active default; a physical Windows anchor uses the platform default on other systems. Legacy edge rounding can differ by a pixel. The deliberate anchor remains separate from roaming and MyGo automatic window-state persistence.

The original vendored Anime4K.js and MIT license are embedded. `assets/anime4k-provenance.json` records the byte-for-byte source paths and SHA-256 identities. The fixed local origin publishes only the explicitly listed scripts; no CDN or arbitrary executable route is introduced.

THA4 retains the reference crop `x=60, y=20, width=390, height=492`. The staged 512px art contains transparent margins, so the visible opaque body can occupy substantially less than its nominal stage; this source-art whitespace is preserved. The compositor performs two RGB bleed passes, the original SIMPLE_M_2X preset and a separate bilinear destination-in alpha mask. If WebGL/SR fails, THA4 continues with the raw crop.

Provider attempts are WebNN, WebGPU with graph capture, WebGPU without capture, then WASM. Only the successfully selected WebGPU provider can receive external GPU buffers. Its constant image tensor stays uploaded and its pose buffer is updated per frame. The first actual `session.run` validates each attempt before selection; creation success alone is insufficient. Failed attempts release their session and buffers. Outputs are disposed once, including aliases, readback failures and close races. RGBA composition still reads GPU output back to CPU; this is not a zero-copy output pipeline.

The THA4 frame now mirrors the final visible image for left-facing feet, preserving the crop, super-resolution alpha and the direction sampled for each asynchronous inference; pickup/throw retain the reference's unmirrored hanging direction. Node fixtures cover successful SR, raw fallback, changing direction while inference is in flight and close/failure cleanup. An owned WebView2 test on this machine compared right/left/right-return frames against the original feet-pivot Canvas formula with matching Canvas context attributes: each same-frame comparison had zero channel differences (`tmp/pet-facing-gui/result.json`). An independent CPU-copy byte-reversal comparison reported up to one channel value on a small number of feathered pixels; this is retained in the record rather than interpreted as exact across context types. Other body-state transforms, pickup geometry and performance remain separate parity work.
